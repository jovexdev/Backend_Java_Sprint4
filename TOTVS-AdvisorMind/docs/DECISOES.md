# Decisões arquiteturais finais

Prioridade: SQL fornecido no chat > funcionalidades reais do Java > documentação anterior. Preservada base Maven/Java21/SpringBoot/JDBC/pacotes. Versão 2.0.0 original mantida separadamente; nova versão 3.0.0 para entregar como FINAL.

1. Todas as seis tabelas são persistidas e consultadas por JDBC direto. T_TOTVS_VENDEDOR não é usada. IDs long gerados pelo banco, recuperados com prepareStatement(sql, new String[]{nome_da_coluna_pk}); não há MAX+1. Os DAOs fecham PreparedStatement e ResultSet com try-with-resources. ConexaoFactory abre conexões Oracle com Class.forName e DriverManager.getConnection, como no professor. URL e conta são configuradas no construtor vazio da própria classe, somente na cópia local; o repositório contém placeholders. ConexaoDataSource e BancoConfig adaptam a factory ao pool; JdbcSupport usa DataSourceUtils para compartilhar a conexão da transação Spring. A conexão transacional só é fechada pelo Spring ao concluir commit/rollback. Ver ALINHAMENTO-JDBC.md.
2. Services coordenam validações e transações. DTOs distinguem entrada de modelo persistido; não recebem IDs gerados, contadores derivados, JSON arbitrário de repositório ou metadados de IA manualmente. As respostas são modelos enxutos com somente campos persistidos, mais DTO específico na prévia.
3. Cliente tem id/dataNascimento. Reuniao usa três IDs relacionais obrigatórios, data e status, sem snapshots. A classe mantém as regras de temperatura/duração. Nascimento LocalDate; reunião LocalDateTime sem offset/fracoes; execução de IA convencionalmente UTC sem offset em Oracle DATE.
4. ReuniaoDao (antes ReuniaoRepository) integra a mesma camada DAO das outras cinco tabelas; JsonUtil somente serializa um índice de IDs derivado. Não há escrita de reuniões em JSON local. REUNIAO é fonte canônica; CLOB e contador são atualizados na mesma transação. SELECT FOR UPDATE nos pais, em ordem de IDs, serializa alterações concorrentes pelos Services. Operações diretas por outros sistemas exigem sincronização explícita.
5. VENDEDOR_REPO é agrupamento de FK com descrição livre; o filtro não é interpretado como SQL e não muda associações automaticamente. Seu total é derivado. VENDEDOR.TOTAL_REUNIOES continua histórico declarado/manual, preservando regras; registrarReuniao() permanece e tem ação explícita na API.
6. Ticket médio não existe no esquema. A fórmula foi preservada com parâmetro BigDecimal, duas casas HALF_EVEN, explicitamente simulação não persistida. No-arg legado lança erro para não inventar resultado. API sem ticket devolve comissão null e explicação.
7. Os três serviços preservam prompts completos na prévia e recebem modo compacto para persistência. Sem truncamento: >250 caracteres/bytes devolve erro, sem gravação. Modelo e tokens vêm do envelope do provedor; ausência não vira valor artificial. Limite de 75 para modelo. Uma análise por reunião/tipo, sem update manual de proveniência.
8. Chamada HTTP ocorre fora da transação. Gravação curta via TransactionTemplate bloqueia/revalida reunião, verifica duplicidade e insere. Sem chave503, externo502/503, timeout504; custo externo não é revertido por rollback. Não há retry pago automático. Transcrição alterada durante análise gera conflito; duplicidade concorrente pode consumir duas chamadas mas não duas linhas.
9. Atualização de reunião com análise bloqueia mudanças nos dados analisados. Exclusões respeitam FKs sem cascata escondida. H2 reproduz FKs/UK/identity e DATE em MODE=Oracle; NLS, charset, collation e driver real precisam de validação Oracle.
10. Validação de VARCHAR2 também em UTF-8 bytes é conservadora para Oracle AL32UTF8 BYTE. Status AGENDADA/ATENDIDA/CANCELADA e tipos1/2/3 são domínios da aplicação baseados nos exemplos; o DDL oficial não recebeu CHECKs adicionais. Anos1..9999 e inteiros até Integer.MAX_VALUE/IDs até Long.MAX_VALUE são limites explícitos da API.
11. Console foi atualizado para os novos dados e compartilha Services. Os sete antigos executáveis de teste manuais, presos ao esquema híbrido, foram substituídos por JUnit e probes Oracle; originais preservados no pacote anterior. JsonUtil antigo não continua como fonte de verdade.
12. Front-End não foi enviado; não há prints fabricados ou integração Data Science alegada. Nome oficial da equipe não comprovado; integrantes e RMs são os da documentação original. A página estática publicada na conversa não é a aplicação Java nem evidência visual desta versão.

Alterações no contrato são necessárias pelo SQL: IDs deixam de ser recebidos, vendedor obrigatório, transcrição4000, empresaCliente100, data/status e novas FKs. Não são mudanças opcionais escondidas. GETs de reunião retornam IDs, não objetos embutidos. Persistir IA retorna201, não200.
